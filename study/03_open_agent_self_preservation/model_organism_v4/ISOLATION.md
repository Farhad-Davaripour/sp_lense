# Version-4 worker boundary: tested before any model job

The separate version-4 root is `/var/lib/sp-lense-r3-organism-v4`; its copied source is under `/opt/sp-lense-r3-organism-v4/code`. The initial **probe-only** root passed its gate before the analysis/audit source was complete and was preserved under a different name, as described in [PRE_MODEL_REBUILD.md](PRE_MODEL_REBUILD.md). The exact documented root was then recreated from the complete committed source. Its [final source manifest](evidence/final_SOURCE_MANIFEST.json) includes the trusted analysis/audit source snapshot; parent adapter hashes remain in [PARENT_ADAPTER_MANIFEST.json](evidence/PARENT_ADAPTER_MANIFEST.json). The pinned base model's 10 files were verified against the prior manifest. The local offline runtime's recorded package versions are copied to the root inputs.

The [final isolation gate](evidence/final_isolation_gate.json) again passed all **21** checks before any version-4 model payload: namespace/socket/host-path restrictions, actual memory/swap/CPU/process limits checked before startup, output quota, 12-GiB memory cap with zero worker swap, 12-core CPU ceiling, 64-process cap, runtime watchdog, and explicit cancellation. The initial [preliminary gate](evidence/isolation_gate.json) remains available for comparison. The benchmark-confirmed training setting is ten Torch threads under this 12-core ceiling. The worker account is unprivileged; Bubblewrap exposes only read-only code, data, runtime, pinned model, private `/proc`/minimal `/dev`/small `/tmp`, and bounded output. Model-facing tools are pure in-memory records and cannot invoke the host shell, network, file-copy, infrastructure, or shutdown operations.

The rebuilt trusted campaign was deliberately invoked without `BACKUP_DESTINATION.json`. It failed **before creating a model job**, with `Durable separate-drive backup destination is required before any new model run`. The root contained only the seven expected `v4-gate02-*` isolation-suite probe jobs. This was a tested historical storage gate, not a failed model experiment. The user subsequently waived the separate-backup requirement, accepted single-drive risk, and explicitly authorized resuming the prepared experiment. The prior control source and gate were copied, not moved, before the updated control was installed; their hashes are in [TRUSTED_CONTROL_REVISION.json](evidence/TRUSTED_CONTROL_REVISION.json). The updated trusted campaign checks the exact C: worktree/raw-storage paths and records [STORAGE_DECISION.json](evidence/STORAGE_DECISION.json).

The [gate on the updated operational source](evidence/gate03_isolation_gate.json) passed all **21** checks again as `v4-gate03`, after the trusted control revision. `campaign.py storage-check` then passed without starting a model. Only after these checks did the unchanged-base diagnostic stage start. Its model outputs and scientific score will be reported separately; gate success is not a behavioral result. No existing version-1 through version-3 evidence was moved, and no cloud service or PR merge is part of this change.

The gate verifies this fixed software and host boundary, not absolute immunity to every kernel or dependency defect. Do not treat an adapter loaded into a different application with real tools as covered by this test. The earlier Research 3 experiment and its evidence remain unchanged.
