# Supervisor replacement: native development runner V2

V1 is retained unchanged and rejected for real use. Its fake tests missed an unwired CLI, a no-op watched child, real work in the unbounded parent, 64-hex-only commit validation in a SHA1 Git repo, and comparing SHA256 file content hashes with Git object IDs. The V1 review did not catch the last two; root confirmed them directly.

V2 is native_development_runner_v2.py plus test_native_development_runner_v2.py. One clear path: default preflight-only; explicit --run runs parent preflight then a watched --worker child; that child repeats preflight, takes an exclusive owner marker, verifies snapshot bytes, imports the fixed real providers, captures and writes exclusive artifacts. Only the parent can create supervisor_success.json, after zero exit, matching PID/token/run/lock identity, output hashes and deadline. No dummy supervisor and no parent capture callback. Failed artifacts are retained without a success receipt; only a matching, confirmed-closed child owner marker is removed. Failure to stop a child leaves its marker blocking another run.

Source checks accept40/64hex Git commit IDs, read exactly each declared commit:path blob and compare its bytes with SHA256-pinned working files. No repository-wide object enumeration. All7 project modules,4package versions/Python/prefix and6critical provider source files are mandatory. This is not hermetic dependency authentication. Input checks use actual public index case_ids/counts, not V1's invented cases schema. TRAIN120/VALIDATION40 status/fold/ancestry/counts are checked, alongside complete192case publicHOLDOUT and a matching whole-corpus audit seal. That seal must expose status PASS, model_outcomes_read:false,private_text_exported:false,dataset_hashes(train,validation,holdout_index); it must be created by the later independent corpus audit, not invented to unblock a run.

The V2 lock schema is native_development_execution.v2. No real --run or native provider import was performed.

Testing caught a Windows venv redirector PID mismatch. launch now uses the base interpreter while preserving the venv through __PYVENV_LAUNCHER__, matching the installed CPython3.12 multiprocessing.popen_spawn_win32 mechanism. Real toy subprocesses confirm the watched PID equals the executing Python PID and sys.prefix remains the selected venv. This concerns process identity, not permission changes. See [CPython's Windows venv launcher](https://github.com/python/cpython/blob/main/PC/venvlauncher.c); the exact local multiprocessing source was also inspected.
