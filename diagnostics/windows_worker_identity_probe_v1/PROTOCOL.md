# One owned Windows interpreter-identity probe

Question: does the exact pinned `.venv/Scripts/python.exe` create an owned launcher plus a different actual Python process, and can that live relationship be authenticated? This is model-free process diagnosis, not a new scientific attempt or a repair to any old evidence.

Freeze and commit this source/protocol/plan before one probe child. The Python driver launches exactly one child using its same pinned venv executable, `-B`, this frozen file and `child`; no shell. The child reports PID/PPID/sys.executable/sys._base_executable and OS image/creation identity, echoes a fresh random nonce received over its private inherited stdin pipe, then waits for a matching acknowledgement. A seven-second self watchdog bounds that wait. While it is alive the parent queries only its owned Popen handle and the nonce-reporting child handle (query/synchronize access only): GetProcessId, NtQueryInformationProcess(ProcessBasicInformation), QueryFullProcessImageNameW, GetProcessTimes. No process enumeration, arbitrary-PID termination, process-tree kill or system changes. Opened child handles are retained until exit to avoid PID-reuse ambiguity; they never receive termination rights.

The parent deadline is ten seconds including owned-handle cleanup. The known cleanup pattern is Popen terminate/wait, then kill/wait only on the exact owned object; never PID-targeted. The child's watchdog separately exits a blocked Python child. Capture only bounded JSON/diagnostic text (16KiB stdout, 8KiB stderr); namespace cap4MiB, file1MiB; invoked work<=90s. On error save the first error and cleanup state, do not retry. No model/transformer/tokenizer/gate/dataset/activation imports or reads. Driver/setup commands do not count as additional owned probe children; the sole Popen call is the declared child.

Prospective relationship test: require distinct wrapper/Python PIDs, child OS parent PID exactly equal to the owned live wrapper PID, wrapper parent PID equal to driver PID, expected wrapper/base image paths and SHA256, matching child self PID/PPID/base path, matching nonce, wrapper creation<=child creation, and both live handles retained until clean zero exit/EOF. A mismatch is diagnostic UNKNOWN/FAIL, never relaxed. The OS process image, not sys.executable alone, distinguishes launcher from interpreter. No claim that the old unrecorded ancestry has now been authenticated.
